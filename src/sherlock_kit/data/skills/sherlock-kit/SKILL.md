# sherlock-kit (`shk`)

`shk` submits and tracks Sherlock jobs by name and moves data through the DTN. Slurm is the only source of truth; `shk` keeps no local state. Operational results print one JSON document with `schema_version: 1` on stdout; `shk rules`, `shk --version` and help print text, and usage errors print text on stderr (exit 2).

## Setup check

1. Prefer the project environment's `shk` (`.venv/bin/shk`, or `shk` and `python -m sherlock_kit` in the activated environment). Not `uv run shk`: it locks and syncs the project environment first. Ask before any `pip install`, upgrade or version switch. A project without `shk` gets, once the user agrees, a dependency on a release tag, never a branch: `sherlock-kit @ git+https://github.com/FridrichMethod/sherlock-kit@vX.Y.Z`; a separate small environment only when the project's Python is older than 3.11 or its environment must not change. An upgrade changes that tag, relocks or reinstalls, and reruns `shk install-skill` with the same options. `shk` releases often: that tag and the lock file are the only places that name the version. Never write it into the project's code, tests, job scripts or guides, compare `shk --version` with a fixed string, or bind the install by a wheel or hashes of the project's own; read replies by `schema_version` and their documented keys.
2. Run `shk --version`: `sherlock-kit X.Y.Z (FORM)`. FORM is `git <commit>` (installed from a tag), `editable <path>`, `submodule <path>`, `source <path>` (a development checkout: never use it for real work) or `unknown`. The controller extensions require shk 0.5 or newer; with an older one, or when a command or flag here is missing, follow `shk <cmd> --help` instead.
3. If no Sherlock rules are loaded in this session, read them first: `shk rules workstation` on a workstation, `shk rules cluster` on Sherlock.
4. `shk doctor` is read-only and offline (`--remote` adds one read-only call on Sherlock).
5. In Codex, a sandbox startup failure or local SSH socket `Permission denied` / `Operation not permitted` does not mean a missing master. Request per-command approval for the blocked command, then retry once; never disable the sandbox or grant writes to all of HOME. Even offline `doctor` needs control-socket access; `submit --dry-run` does not. On Sherlock, per-command approval is expected because the Codex sandbox cannot start there.

## Exit codes

| Code | Meaning | Do |
|---|---|---|
| 0 | ok | continue |
| 1 | config, spec, verification, validator, malformed reply, failed remote read | fix input errors before retrying; for `malformed_read`, follow its hint if present (one read retry after 60 s; `shk doctor --remote` checks remote tools) |
| 2 | usage error | read `shk <cmd> --help` |
| 3 | refused, and nothing was submitted, cancelled, released, requeued or updated: live duplicate, finished task without `--resubmit`, missing `--courtesy-ack`, `dev` (no batch jobs), an `#SBATCH` directive shk owns, a borrowed `update` target, a remote guard that stopped before `sbatch`, `scancel` or `scontrol` ran, a `--preflight` request that Slurm rejects, push or pull on Sherlock | read the message; change the request, not the guard |
| 4 | SSH transport or master check unavailable | Local permission denial: follow Setup check 5. `auth_required`: ask the user to run the hint (`ssh sherlock-plain`, or `ssh -fN sherlock-dtn`), then retry once. `unavailable` with a `~/.ssh/config` hint: the client config needs fixing; logging in again does not help. Other `unavailable` or `timeout` (hint `run shk doctor`): run `shk doctor`, retry once after about a minute, then stop and tell the user |
| 5 | outcome unknown after a dispatched submit, cancel, release, requeue or update: `sbatch` ran without printing a strict job id, `scancel` exited nonzero, `scontrol` exited nonzero in `release` or `requeue`, `scontrol update` was dispatched and the re-read failed or did not show the requested value on every record, or the reply was lost. `detail` carries the evidence, such as `sbatch exit RC` or `scontrol update exit RC` and Slurm's text | run the `shk status` command in the reply's `next`, not before the time it names (at least 60 s); never resubmit or repeat a mutation blind |
| 6 | status ok, but the newest job of a name has an anomaly | stop and report it to the user |

## Configuration

`shk` reads `[tool.sherlock-kit]` from `pyproject.toml` (or top-level keys in `sherlock-kit.toml`) in the nearest directory at or above the working directory that has one; from elsewhere pass `--project-dir DIR`. Keys: `project` (required to submit), `remote_root` (absolute Sherlock path, required to submit and, without `--anywhere`, to push), optional `control_host`, `data_host`, timeouts and `[tool.sherlock-kit.validators]`. Unknown keys are errors. Never put secrets there. The configuration describes the project; the pin, not the configuration, decides which shk runs. Prefer the `pyproject.toml` table when the project has one: in one directory it wins over `sherlock-kit.toml`.

## Short work

A check of seconds, an environment build, a compile, a CPU or GPU test of a few minutes or a project's test suite runs on the first rung that can hold it. Sherlock's numbered rules decide; nothing here widens them.

1. Workstation: CPU test suites, lint, `shk submit --dry-run`.
2. Login node, directly or over `sherlock-plain`: reads, checks of seconds, small pure-Python installs; never compiling, Conda, CUDA or ML stacks.
3. One `dev` run: compiling, heavy installs, tests beyond seconds, a GPU smoke test.
4. A short batch job through `shk submit`: whatever exceeds `dev` (time, memory, the production GPU class).
5. The production job.

A `dev` run is one blocking `srun`. From a workstation it goes over the master with the local script on stdin, so nothing is staged (first line); on a login node run the second line. `bash -l` gives the script `module`, `ml` and `sh_part`.

```sh
ssh -oBatchMode=yes -oProxyCommand=false sherlock-plain \
  'srun --partition=dev --time=10 --cpus-per-task=2 --mem=4G bash -l -s' < check.sh
srun --partition=dev --time=10 --cpus-per-task=2 --mem=4G bash -l -s < check.sh
```

- Request explicitly: `--time` in minutes close to the expected runtime (site rule 2), CPUs and memory. `dev` allows 2 h at most (1 h default), and a request above a partition's limit pends, possibly indefinitely, or is rejected where the site enforces partition limits at submission (Slurm's documented behavior; not observed on Sherlock), so never ask for more. `--mem=4G` is `sh_dev`'s own default and fits both per-user caps the site documentation states ("4 cores + 2 GPUs/user", "2 cores and 8 GB"); neither cap is observed. Read the limits with `sh_part` in a login shell.
- A GPU smoke test adds `--gpus=1`. The GPUs of `dev` are A30 MIG slices of 6 GB: they prove imports, CUDA visibility and a small forward pass, not memory fit or throughput on the production GPU, which take a short batch job on the target partition. GPUs on `dev` are not observed by the kit, which never submits GPU work while it is developed.
- One run per task: put every pending check of the task into the one script (site rule 10 asks to aggregate short tasks). Never a planned series of short runs, a retry loop or padding; one rerun after the cause of a failure is found is fine.
- One blocking, attended call: in the foreground, or as a background command that the harness tracks, with a tool-call timeout above `--time` plus a start allowance. Never `nohup`, a plain `&`, `tmux`, `screen` or `salloc --no-shell`.
- `sh_dev` takes no command and opens an interactive shell; a command given to `salloc` runs on the login node where `salloc` was invoked. Neither is the agent's path. A user may open `sh_dev` and run the agent inside it: that session is an allocation to use fully.
- Observed, CPU only: the call needs no pty, srun printed the job id on stderr (`srun: job N queued and waiting for resources`) before the script ran, the call returns the script's exit status, the run started within seconds, and a `dev` node reached PyPI, GitHub and conda-forge. By Slurm's source srun prints that line only for a request that queues, as both runs did, and no id for an allocation granted at once: begin the script with `echo "job $SLURM_JOB_ID"`, so that after a lost call N is in the stderr or the stdout received so far.
- A lost or killed call leaves the job running and its `srun` client on the login node (observed 75 s after the kill); unless cancelled, both last until the script ends or the time limit (inferred). Wait 60 s and read the job once with `shk status --job-id N`; if it is still `live` (pending or running), end it with `scancel N`, that exact id (over `sherlock-plain` from a workstation; `shk cancel` addresses only shk job names), and move work that does not fit a bounded call into a batch job.
- `--immediate=SECONDS` bounds the wait for an allocation: Sherlock accepts it (observed); its refusal path is not observed. Without it a request that cannot start pends and the call blocks.
- When `dev` cannot serve the work (more than 2 h, more than its per-user caps, the production GPU class, a call the session cannot hold), run a short batch job through `shk submit` (`--dry-run` first, then one bounded `shk wait`), aggregated to 10 useful minutes or more, for example the test suite with the first production-sized unit; never pad.
- Record the job id, node, exit status, versions and loaded modules, and timings; say whether a GPU result comes from a `dev` slice.
- A consuming project's own guide points at this section instead of restating where short work runs.

## Submit

```sh
shk submit --task train-a --script job.sh --partition normal --cpus 4 --mem 16G --time 2h --dry-run
shk submit --task train-a --script job.sh --partition normal --cpus 4 --mem 16G --time 2h
```

- Always `--dry-run` first: it is offline and prints the job name, the sbatch argv and the frozen spec.
- The name is `shk.<project>.<task slug>.<hash>` from project, `--campaign` (default `default`) and `--task`. The same task always gets the same name, so a second submit is refused (exit 3) while a job of that name is pending or running, even with `--resubmit`.
- A done or failed task is refused unless `--resubmit "<reason>"` names why it runs again; find the cause of a failure first.
- Once `sbatch` has run there are two outcomes. `submitted` (exit 0): the stdout of `sbatch` was, trailing newlines aside, one strict job id line (`N` or `N;CLUSTER`, matched as ASCII digits whatever the login locale), even if `sbatch` exited nonzero (`sbatch --wait` returns the job's exit code). Anything else is exit 5 `action: unknown`, never a refusal: `detail` holds `sbatch exit RC` and Slurm's stderr text, and the staged `NAME.STAMP.sh`, `.json` and `.err` stay in `<run-dir>/.shk/`. A Slurm error message after dispatch does not prove that no job exists: run the `next` status command after 60 s. A name whose submission never landed reads `stale` and submits like `new` when it has no earlier job in the 30-day window that submit reads; when it has one, it keeps that job's `done` or `failed` state and `current.job_id` and still needs `--resubmit`. The attempt landed only if `current.job_id` is newer than the one seen before the submit. For a definitive Slurm verdict without a job, use `--preflight`.
- Deduplication reads only `squeue` and the last 30 days of `sacct`. A task whose jobs are older than that submits again as new, without `--resubmit`, even when its run directory still exists: check before rerunning old work.
- Partition, CPUs, memory and walltime are explicit. GPUs only with `--gpus N` on a partition that allows them; `--constraint` instead of excluding nodes. `--constraint`, `--prefer` and `--signal` go to sbatch unchanged, and one that is given but empty or whitespace-only (an unset shell variable) is refused offline, exit 1 `spec_invalid`. Requeue only with `owners`, alone or in a set; the script of every job that can start on `owners` must checkpoint periodically. `dev` takes no batch jobs (Sherlock rejects them, so submit refuses it, exit 3): for a quick test or build there, see Short work.
- `--partition` takes one partition, or compatible partitions as one comma-separated value: `--partition gpu,bioe,stat` lets Slurm start the job in whichever member can start it first (Slurm's documented behavior). A repeated `--partition` flag is not a list: the last one wins. A set is compatible when every member is listed and takes batch jobs, none is borrowed, and, with `--gpus` above 0, every member allows GPUs. So `owners`, `gpu`, `bioe` and `stat` combine, `normal`, `bigmem` and `service` combine too, and `btrippe` and `possu` stay alone. A set states that the job may run on any member, so it follows every member's rules and courtesy text wherever it starts. A set with `owners` is preemptible and requeues by default, so its script needs the same-command resume that `owners` needs even when the attempt starts on another member; a job that names `bioe` or `stat`, alone or in a set, falls under their courtesy text. Submit checks the members offline, in this order: an unlisted or empty member is exit 3 `unknown_partition`; a repeated member is exit 1 `spec_invalid`; a member without batch jobs (`dev`) is exit 3 `batch_not_allowed`; a borrowed member is exit 3 `partitions_incompatible` (submit a borrowed partition alone). Then `--gpus` above 0 with a member without GPUs is exit 3 `gpus_not_allowed`. Requeue defaults to on when a member allows it (`owners`); `--no-requeue` is accepted, and `--requeue` on a set without such a member is exit 3 `requeue_not_allowed`. The rules' "Requeue only where `requeue=yes`" is read per submitted value: a set with a `requeue=yes` member is submitted requeueable and stays so on every member, `shk requeue --self` included. The frozen spec keeps the value as given in `resources.partition` and adds the member list `resources.partitions`; the job name does not depend on the partition. Only `submit` and `update` take a list: `resources` and `occupancy` take one name per `--partition` flag. shk 0.7 and older report `unknown_partition` (exit 6) for a job submitted with a list while Slurm prints the list. A real submission with a list is not observed live on Sherlock; `--preflight` accepted `owners,gpu` and `owners,gpu,bioe,stat` (2026-11-25). Try a list with `--preflight` first. That checks Slurm's creation-time verdict and names one partition that can run the job; it does not prove that a real submission is accepted or that every member is usable.
- The job runs in `--run-dir` (default `<remote_root>/runs/<name>`), which keeps `.shk/<name>.<jobid>.sh` and `.json` as provenance. `#SBATCH` lines in the script may not set what shk owns, in any form sbatch accepts (`-p`, `-H`, `--part`, ...): account, exclude, GPUs or gres, partition, array, dependency, begin, job name, hold, and comment when `--submission-token` sets it; heterogeneous jobs (`hetjob`, `packjob`) are refused.
- `--preflight` (mutually exclusive with `--dry-run`) reads Slurm validation using `sbatch --test-only`, creates no job or provenance, and retains returncode/stdout/stderr; quota refusal is exit 3; a controller transport failure (`Unable to contact slurm controller`, socket timeouts) is exit 1 `malformed_read`: retry once after 60 s. Read failures are never unknown. The reply adds `estimate` right after `preflight`, read from Slurm's line `Job N to start at TIME ... using N processors on nodes NODES in partition PARTITION`. Its `status` is `parsed` (exactly one such line, with a `YYYY-MM-DDTHH:MM:SS` time: `start`, `nodes`, `partition` and `line` are set), `absent` (no such line and no line holding ` to start at `, as for an accepted call without an estimate or a rejected one, which `ok` and the exit code tell apart: `start`, `nodes`, `partition` and `line` are null) or `unparsed` (anything else, such as `Unknown` or two estimate lines: only `line` is set, nothing is guessed). `start` is Slurm's text without a zone, and `start_zone` is `sbatch-local`: the local time of the `sbatch` process on the executor host, the site's zone unless `TZ` is set in that session. `observed_at` is UTC, equal to `queried_at`; `nodes` is a hostlist expression as printed. The estimate is advisory, not a reservation or a promise. For a partition list Slurm names the first partition, in its own priority order, that can run the job and estimates its start there: that is not the earliest start over the set (the line for a list is not observed live). To compare partitions, run one preflight per partition, for a bounded set. The job id in the line belongs to a temporary record; no `estimate` key holds it.
- `--submission-token TOKEN` sets a public Slurm Comment, exported to the job as `$SHK_SUBMISSION_TOKEN`; `--hold` needs a token and sets a user hold for `shk release`. Both are frozen in the spec.
- `--cpu-thread-budget [N]` (N defaults to 1 and is at most `--cpus`; or project `cpu_thread_budget = N`) runs sbatch under `env` with the OpenMP, MKL, OpenBLAS, BLIS, vecLib and NumExpr thread variables set to N, also with `APPTAINERENV_` and `SINGULARITYENV_` prefixes, and records `cpu_thread_policy` in the spec. These are launch defaults, not an OS-thread limit. A script that sets only `OMP_NUM_THREADS` (for example `OMP_NUM_THREADS=$SLURM_CPUS_PER_TASK`) stays capped by `OMP_THREAD_LIMIT` and the library-specific variables: the lever for more threads is a larger `--cpu-thread-budget N`. A submission made from inside a budgeted job inherits its variables through `--export=ALL`, so a nested submission passes its own `--cpu-thread-budget N`. A controller that checks the argv must accept its `env` prefix.
- Chain stages with `--after-ok JOBID` (repeatable; several ids separated by spaces, never commas) instead of polling. Bounded deterministic compute controllers inside a Slurm allocation may call `shk --executor local` for authorized later compute stages, without a workstation; never schedule future agent/LLM sessions.

## GPU and partition preferences

These owner defaults guide agents; they do not inject CLI/TOML defaults or change site restrictions. Explicit task requirements and site policy take precedence. Discover actual features with `sh_node_feat` and partition limits with `sh_part` in a login shell. Prioritize the earliest start, and choose by expected time to completion, including queueing, startup, computation and recovery, not peak GPU speed alone. Before GPU submission, compare viable CPU and host RAM requests with one fresh `shk resources --partition P --summary --by sku --shape name:cpus=N,mem=SIZE,gpus=1` snapshot. Compare slots for eligible GPU features only. All requested GPUs, CPUs and scheduler memory must fit on the same node. Set CPUs to the useful thread count and host RAM to measured peak use plus headroom. A shape that fits more nodes can shorten the wait. Keep only the memory, kernel and dtype requirements that have real evidence, and the site rules.

Start with a broad compatible OR constraint. The discovered production candidates include:

```text
GPU_SKU:A100_PCIE|GPU_SKU:A100_SXM4|GPU_SKU:A40|GPU_SKU:H100_SXM5|GPU_SKU:H200_SXM5|GPU_SKU:L40S|GPU_SKU:RTX_3090|GPU_SKU:TITAN_V|GPU_SKU:V100_PCIE|GPU_SKU:V100S_PCIE|GPU_SKU:V100_SXM2
```

Pass the compatible subset as `--constraint 'GPU_SKU:...|GPU_SKU:...'`, with explicit partition, GPU count, CPUs, memory and walltime. This is a starting set, not a permanent allowlist: include newly discovered compatible GPUs. Avoid RTX_2080Ti and Pascal-era P100/P40/TITAN_Xp by default. TITAN_V has only 12 GB and RTX_3090 24 GB; narrow by actual memory, CUDA architecture, kernels and dtype requirements, with a concrete reason. Small MIG slices must fit the task and their partition's rules; the 6 GB A30 slice in interactive dev is not a production batch fallback.

Use `shk submit --prefer` for a soft preference over the compatible, discovered
L40, A and H families and future B or newer families. They form one preferred
tier; OR order does not rank those families. The tier is purely a
compute-capability ordering, so it applies across projects. `--prefer` is soft:
Slurm tries it first, then the fallback `--constraint`. With the candidate
inventory above, the preferred expression is:

```text
GPU_SKU:A100_PCIE|GPU_SKU:A100_SXM4|GPU_SKU:A40|GPU_SKU:H100_SXM5|GPU_SKU:H200_SXM5|GPU_SKU:L40S
```

Keep the broader compatible set in `--constraint` so other acceptable GPUs can
run when the preferred set is unavailable. Slurm tries `--prefer` independently
before `--constraint`, not as their intersection: the preferred set must be a
subset of the allowed hardware and both expressions must include every hard
memory, architecture or other feature requirement. Adapt both lists to the task;
add a future SKU only after discovery, never by guessing a feature or using a
family wildcard. This does not reserve GPUs, promise a start time or justify
waiting indefinitely for a preferred card. See the
[Slurm sbatch reference](https://slurm.schedmd.com/sbatch.html#OPT_prefer).

GPU models are scientifically equivalent: they may be mixed, and a job may get another model after a requeue. The model alone is no reason for new controls, cohorts, reruns or per-model qualification. Default scientific comparisons may combine compatible GPU models; record actual hardware as provenance without adding controls, cohorts or reruns solely for the SKU. This does not promise bitwise equality or certify software compatibility. Keep effective inputs, model/checkpoint, seeds, numerical settings and environment protocol fixed. Validate a real compatibility uncertainty when needed, without requiring every model/SKU combination before independent ready work progresses.

Consider authorized department partitions (bioe/stat), resumable owners and public gpu using measured throughput and queue/resource evidence. A compatible set such as `--partition owners,gpu` or `--partition gpu,bioe,stat` lets Slurm start the job in whichever member can start it first (see Submit); the borrowed partitions stay alone. Observed on Sherlock with `scontrol show partition` (2026-11-25): bioe and stat have PriorityTier 1000, gpu and normal 10, owners 1; owners is the only one with PreemptMode REQUEUE (GraceTime 0), the others OFF; every bioe and stat node is also an owners node, no gpu or normal node is; MaxTime is 2 days on owners and gpu and 7 days on bioe, stat and normal; bioe has 20 GPUs, stat 8. The members of a pending set are tried department partitions first, then gpu, then owners. A record waiting in `bioe` or `stat` can preempt `owners` jobs on that department's nodes, your own included (Slurm has no same-user exemption: source-confirmed; such a preemption is not observed). A requeued job keeps its whole list and can start on another member and another GPU model (Slurm source, not observed live). The kit sets no number for `owners,gpu`; Slurm does: every pending task of a set that lists `gpu` counts against the submit limits of the gpu partition QOS, per user and per account, until it starts (Slurm source; Sherlock's values are not verified). Before a real submit of a set that lists `gpu`, run the same request with the real `--array` under `--preflight`, and send work beyond what gpu admits to `owners` alone. A set that names `bioe` or `stat` is sized for the department partition, not for `owners`. Read `shk occupancy --partition bioe --partition stat` first (see Occupancy below). Bound what you can run there from your own live submissions that name the partition: the sum of min(tasks, `%M`) times GPUs per task. Raising a throttle with `shk update --throttle`, releasing a held job that names `bioe` or `stat`, or moving a job onto them with `shk update --partition` is the same decision as a submission. Submit the rest to `owners,gpu` or `owners` as different work units, never the same unit twice. `shk resources --summary` and the `--preflight` estimate help judge where work can start, within the limits that Controller evidence and Submit state: a snapshot and an advisory estimate, neither a reservation. Borrowed btrippe/possu follow the Occupancy section below unchanged: btrippe has no blanket daytime prohibition; possu keeps its 00:00-07:00 Pacific window. Before owners, alone or in a set, prove same-command idempotent recovery with durable checkpoints, complete-output verification, retained interrupted attempts and bounded no-progress retries. Slurm requeue restarts a script; it does not restore application state. Do not depend on a usable preemption signal window.

## Parallel GPU campaigns

These are project-controller responsibilities; Kit keeps no campaign ledger and does not certify scientific results. Use one coordinator; hold its durable lock only for short state/intent transactions, not while waiting for workers or agents. Persist leases and PID plus process start identities, and verify unresolved launch outcomes before replacement dispatch; a stale heartbeat alone does not prove a worker stopped.

- Freeze inputs, sources/checkpoints, numerical settings, seeds and complete per-unit budgets. Track every planned unit in preparing, ready, queued, running, unknown-held, blocked, accepted or failed states, with a unique owner, epoch, blocker and next action. Keep failed or unavailable lanes in the denominator; separate accepted outputs from all-attempt outputs.
- Run ordinary CPU preparation, feature checks and recovery tests locally in parallel. Stage required assets before dispatch. Keep mandatory allocation/environment/provenance checks in jobs. On Sherlock, installs, builds and tests run where Short work places them; never production work on `dev`. A general CPU test suite need not occupy each GPU job's startup path.
- Define admission lanes by model/source/runtime, required features, numerical settings and actual compatible hardware. Record an authorized target of unique live remote bundles and local workers, separate from hard campaign/pilot caps; the pilot cap limits only unadmitted pilots, not admitted production jobs. Reserve one first-pilot slot per unadmitted lane. Pending, held, running, unknown and auto-requeue-pending jobs retain reservations; renamed bundles or changed fingerprints do not bypass caps. Bound technical retries and no-progress requeues.
- Queue CPU-ready independent first pilots as they become ready, without waiting for another lane's pilot or all CPU preparation to finish. Block only lanes sharing the failed dependency. Do not prevalidate every model/GPU combination; add hardware admission when ready work needs it.
- Before scaling a lane, validate a complete production-sized unit through the real launcher/container, actual worker, native model, output checks and verified export/ingestion. Record resolved settings, source/checkpoint, actual GPU feature, full output count/hashes, walltime and peak memory. Connection, preflight, imports and allocation proof are not model runtime acceptance. A passed pilot admits its configuration over the compatible OR set already narrowed by hard requirements; validate a member separately only for a concrete open uncertainty there (less memory headroom than the pilot's GPU, or kernel, dtype or CUDA-architecture support actually in doubt for that member; a different SKU or architecture alone is no such doubt), since a pass on one GPU does not prove headroom on a smaller one.
- Use `--after-ok` as an admission gate only when predecessor success includes the required validation; an entire bundle dependency waits for its last unit. A project can gate continuation inside its bundle or release a verified held successor, within the existing release rules. Bundle sequential units to amortize queue waits and setup; recovery units need not be individual scheduler jobs. Prefer longer useful, resumable allocations when repeated queueing dominates. Do not fragment every sample into a job or inherit a two-hour cap from examples; respect actual partition/courtesy limits and measured runtime.
- At bounded decision points, follow Status and Wait below, batch due reads at least 60 seconds apart, resolve unknown outcomes from Slurm evidence first and collect immutable completed-unit exports promptly. Fill idle compatible local capacity with independently owned ready work and refill admitted remote lanes toward the authorized live-bundle target. Below target, report ready-but-unsubmitted count, age and reason; queued reservations are not running GPUs. Periodically inspect batched status/resources evidence, measured runtime and frozen requests at bounded decision points (at least 60 seconds apart) before a queue/resource-based rebalance; free-looking resources are not a start-time guarantee. A pending job moves to a partition or set that `shk update --partition` accepts (its rule is in Controller evidence below), without a cancel and resubmit. Preserve scientific budgets.
- Transfer ownership only after complete terminal/nonrestartable evidence or a durable project revocation ACK that stops old claims/writes and survives requeue. A cancellation ACK alone is insufficient. Publish the new epoch before dispatch; reject stale claims and accepted-result writes. Pending jobs and unresolved dependencies still own their units.
- Resume the same bundle command. For fixed-size seed units, skip only complete verified outputs; rerun an interrupted unit with the same seed and full budget in a new attempt, without merging partial samples. Complete low-quality predictions are not technical failures to retry for a better score.
- Give delegated work a writer, deliverable and explicit wake-up action; a message to an idle agent may not start it. Report actual running/queued/ready/blocked counts and their full denominator. Separate coordination delay from scheduler wait, and native walltime from allocation GPU-seconds; neither proves measured GPU utilization. Do not schedule future agent/LLM sessions in Slurm.

## Arrays

For many independent tasks submit one array: `--array N[%M]` runs N tasks (2 to 1000), optionally at most M at a time (`shk update --throttle M` changes M later, in any state); each task reads `$SLURM_ARRAY_TASK_ID` (0 to N-1) and logs to `slurm-%A_%a.*`. Size tasks to at least 10 minutes of real work, ideally 30; never pad with `sleep`.

## Status

```sh
shk status --task train-a
shk status --all
```

- At least 60 s between checks; respect `next_check_after` in every submit, status, wait, cancel, occupancy and resources reply. Read the local UTC clock before the next check instead of estimating elapsed time. One `shk status --all` (or several `--task` in one call) instead of a loop per task. Read status by hand only when needed (a wait exited, the user asks, an exit 5 `next` is due) and otherwise rarely, ideally 10 minutes or more apart. Never `watch` or loop `shk status`: to be woken when jobs end, run one `shk wait` (see Wait below).
- `--since DAYS` sets the `sacct` window, 1 to 31 days (default 30, 7 with `--all`; Sherlock refuses wider windows). With several `--task`, give `--campaign` once for all of them or once per `--task`.
- States: `new` (no job), `live` (pending, running or completing; throttle-held array tasks count as pending), `done` (all tasks completed), `failed` (finished, at least one task not completed), `stale` (provenance files but no Slurm rows in the window; treated as `new`). Without a spec file (`--all`, `--name`, `--job-id`) an array whose seen tasks are not exactly 0..max has null task counts, and `done`/`failed` describe only the seen tasks.
- `current` describes the newest job of the name (tasks, exit codes, restarts, cost); older jobs are in `history`. An anomaly such as `unexpected_preemption` or `duplicate_live` gives exit 6: stop and report.
- `current.partition` is Slurm's partition text of the job's first row (queue rows before accounting rows, in Slurm's order). For a single job submitted with a partition list it is the list while pending, in an order Slurm may change, and the run partition once started; a job cancelled while pending shows one member in `squeue` and the list in `sacct`. For an array, or a requeued job read from accounting only, it is one row's text, can change between reads and says nothing about the other tasks or attempts. `status --task` reads the job's frozen spec from its run directory (plain or with `--details`); when that spec lists several partitions, `current` adds `ran_on` directly after `partition`: the sorted distinct partitions in which a task or attempt started, `[]` while no row shows a start. Without a spec (`--all`, `--name`, `--job-id`) there is no `ran_on`: `current.partition` is the first row's text, which for an array whose tasks started on different members names only one of them or the pending list. The per-row partition of `status --details`, or `--task`, tells where each ran. `unknown_partition` checks every member of a list on every row of the job. `unexpected_preemption`: a PREEMPTED attempt on a listed non-preemptible partition, or on a comma list whose members are all such. A NODE_FAIL or REQUEUED attempt and a restart whose earlier attempt is not visible are not anomalies; they show in `max_restart`, `tasks.by_state` and `tasks.incomplete_history`. What `squeue` and `sacct` print for a job submitted with a list is source-confirmed Slurm behavior, not observed live.

## Wait

```sh
shk wait --task train-a --timeout 12h
shk wait --task train-a --task train-b --timeout 24h --interval 10m --max-pending 6h
```

`shk wait` watches jobs so that an agent spends no turns on queued work: after a submit, either end the turn and check when the user asks, or run one bounded wait and act on its outcome. It is read-only: it dispatches no mutation and writes nothing, locally or on Sherlock.

- Selection is that of `shk status`: `--task` or `--name` (both repeatable) or `--all`, with `--campaign`, `--run-dir` and `--since` as there; there is no `--job-id` and no `--details`. The global options apply as for status, with either executor.
- `--timeout DUR` is required, from 1 minute to 168 hours. `--interval DUR` (default 5m, at least 1m) is the delay between reads; `--max-pending DUR` (at least 1m) is off unless given. DUR takes the forms of `submit --time` (`2h`, `90m`, `H:MM:SS`); any other form or an out-of-range value is exit 1 `spec_invalid`.
- Each read is exactly the read `shk status` makes for the same selection. The first read comes 60 s after the wait starts, so a wait may start right after any shk reply (a submit, a status read, an ended wait), and consecutive reads are always at least 60 s apart. While no selected name has a running task and the state is unchanged since the previous read (per name: state, current job id, task counts), the delay doubles, up to the larger of 30 minutes and `--interval`; a running task or any change resets it to `--interval`. With `--max-pending` a sleep is cut so that the next read falls on the earliest name's bound, never sooner than 60 s after the read before it; the delay itself is unchanged.
- Nothing is printed until the end, and `wait` writes nothing to stderr itself (a Sherlock login banner reminder still goes there once, as for every command). The reply is the last read's status payload unchanged plus `wait`: `outcome`, `names` (the names that decided it; `[]` for `settled` and `timeout`), `reads`, `started_at` and `timeout_at` (UTC, in the format of `queried_at`).
- A read that fails (exit 1 `malformed_read` or a configuration error, exit 4, ...) ends the wait with that error reply and exit code; it does not retry.

After every read the first matching outcome decides:

| `wait.outcome` | Exit | Meaning | Do |
|---|---|---|---|
| `anomaly` | 6 | the current job of a name in `wait.names` has an anomaly | stop and report it to the user |
| `failed` | 0 | a listed name is `failed`, at any read, the first included (with `--all`: one that this wait saw `live`); the wait ends at the first failure, so other names may still be live | diagnose first (`shk status --task T --details` from the reply's `next_check_after` on, the Slurm logs in the run directory); resubmit with `--resubmit "reason"` only once a cause is found, then wait again for the rest |
| `settled` | 0 | no selected name is `live` | check that every name is `done` (a `new` name settles too, and with `--all` one that failed before the first read), then pull its outputs |
| `max_pending` | 0 | with `--max-pending`, a live name's current job showed no running task at every read for at least that long | consider `shk resources --partition P --summary` and `shk update` (a partition or set it accepts, constraint or prefer, a shorter walltime), or another wait |
| `timeout` | 0 | none of the above before `--timeout` (the wait ends once less than 60 s of it remains) | run another wait, or end the turn and report the state |
| (error) | 1, 4, ... | the read failed | act as the exit code table says |

- With `--task` or `--name`, a listed name that is already `failed` ends the wait at its first read: list only the names you still wait for. With `--all`, only a job that the wait saw live gives `failed`; an older failure, or one before the first read, does not.
- A held job (`submit --hold`, or a requeue hold) stays `live`: without `--max-pending` the wait runs until its timeout.

Run it from an agent so that it costs no turns and still ends by itself:

- Run it as a background command that the harness itself tracks and whose exit it reports, and do nothing for it until then (Claude Code: Bash with `run_in_background`; do not read its output file while it runs). A shell `&` is not one: nothing reports its exit, and it can outlive the session. Where the harness reports no such exit (in Codex, for example, nothing wakes you when a background command ends), either run the wait in the foreground with a `--timeout` safely within the tool-call limit, leaving room for one read, or end the turn and check when the user asks; never start it with `&` and never poll its output.
- Run at most one wait at a time, over every name to watch (repeat `--task`, or `--all`). After a further submit, let the running wait end, or stop it (it is read-only) and start one wait over all names. Prefer repeated `--task` here: a restarted `--task` wait reports a name that failed in between at its first read, while an `--all` wait does not, so after one check every name's state.
- Never detach a wait so that it outlives the session (`nohup`, a plain `&`, `setsid`, `disown`, a `tmux` or `screen` session left running, cron), never use it to restart or re-prompt an agent, and never schedule a later agent session. On a Sherlock login node run it only in the attended session; inside an allocation a bounded deterministic controller may run `shk --executor local wait`.
- Between stages prefer `--after-ok` dependencies to waiting.

## Inspecting a running job

Site rule 5 allows it: "To reach a compute node, `ssh` to it from a login node while you have a job running there." Use it for what the logs in the run directory and `shk status` cannot show: GPU load and memory, a process that hangs, files in the node-local job directory. The node is the `nodes` field of the job's record under `details.queue` (or `details.accounting`) in `shk status --task T --details` (for a multi-node job a host list expression).

From a workstation the look goes over the master with the local script on stdin (first line); on a login node run the second line.

```sh
ssh -oBatchMode=yes -oProxyCommand=false sherlock-plain \
  'ssh -oBatchMode=yes -oConnectTimeout=20 NODE bash -s' < look.sh
ssh -oBatchMode=yes -oConnectTimeout=20 NODE bash -s < look.sh
```

- One bounded call per look, with every check in the one script and a tool-call timeout: `nvidia-smi`, `ps -u "$(id -u)" -o pid,etime,pcpu,rss,args`, a stack dump of your own process, `ls` or `tail` in the node-local job directory. Never `watch`, a loop, a session left open, `tmux` or `screen` (site rules 1 and 10). Look again only when something needs it, never on a schedule.
- Light work only. The session's processes run inside the job's own allocation (observed: the job's cgroups, and `nproc` 1 for a 1-CPU job), and by the site's documentation what they use counts toward the job's limits, so a memory-heavy command there can end the job. That documentation also allows running additional processes there; the toolkit keeps the session to inspection and debugging, and work belongs in the job script.
- Inspect only your own processes and never kill one there (site rule 6): end a job with `shk cancel`.
- The session is a non-login shell without a tty (observed). `SLURM_JOB_ID` is set, to the job the session joined, and is its only `SLURM_` variable; `module`, `ml`, `$SCRATCH`, `$GROUP_HOME`, `$L_SCRATCH_JOB` and `TMPDIR` are not set. `bash -l` there adds `module` and `$SCRATCH`, not `$L_SCRATCH_JOB`: have the job script print `$L_SCRATCH_JOB` and address that directory by its path, which the session can list and read.
- The login node reached the node without a password or a prompt, and the script's exit status is the call's (observed).
- The session ends with the job: one that was still open when the job ended was closed within about a second, and the local call returned 255 with `Connection to NODE closed by remote host.` (observed). A 255 during a look may therefore mean that the job ended: read `shk status` once, at the usual cadence, before anything else.
- Not observed: GPUs in a session (the kit never submits GPU work while it is developed; the session sits in the job's device cgroup, so `nvidia-smi` should list only that job's GPUs), a multi-node job, and a node that runs two of your jobs. For the last, by Slurm's `pam_slurm_adopt` documentation a session from a login node joins the newest job on the node unless the site configures otherwise; `SLURM_JOB_ID` in the session says which job it joined. Without a job on the node the site refuses the connection (`Access denied by pam_slurm_adopt: you have no active jobs on this node`, site documentation): never try a node that the job's record does not name.

## Controller evidence and exact mutations

- `shk resources --partition owners` (repeatable partition) reads node state, features and configured minus allocated CPU/memory/GPU capacity per node. Count free capacity only on nodes with `schedulable: true`: DOWN, DRAIN, NOT_RESPONDING and similar states make it false, and null means unknown. Missing facts are null and `complete: false`; a failed read is exit 1 `malformed_read` (retry once after 60 s); OS FreeMem never substitutes. It is a snapshot, not a reservation. Large partitions (`owners`: about 1700 nodes) return megabytes of JSON: filter it rather than reading it whole.
- `shk resources --partition gpu --partition bioe --summary [--by sku] [--by class] [--shape NAME:cpus=N,mem=SIZE[,gpus=N] ...]` reads the same single snapshot, keeps `complete`, `malformed`, `queried_at`, `next_check_after` and `provenance`, and prints `summary` in place of `nodes`; without `--summary` the reply is the full node list as above. `summary.union` counts every shipped node once, `summary.partitions` has one group per requested partition, and `overlapping_nodes` counts the nodes that list more than one requested partition. A group counts `nodes`, `schedulable_nodes`, `countable_nodes`, `unschedulable_nodes` and `unknown_nodes`, sums `configured`, `allocated` and `free` of `cpus`, `memory_mb` and `gpus`, and gives `slots` per shape. `--by sku` and `--by class` (repeatable, one value each) add `by_sku` and `by_class` entries keyed by the exact sorted set of a node's `GPU_SKU:` or `CLASS:` feature values, so a node with two SKU features gives its GPUs to no single-SKU entry. A shape is one slot on one node: a unique NAME of 1 to 32 letters, digits, `_`, `.` or `-` that starts with a letter or digit, keys in any order, `cpus` at least 1, `mem` as for `submit --mem`, `gpus` 0 unless given; `slots` is the sum over countable nodes of the smallest of free CPUs, memory and, when the shape asks for GPUs, GPUs, each divided by the shape's amount and rounded down. `--by` or `--shape` without `--summary`, or a bad shape, is exit 1 `spec_invalid` before any remote call. `summary.rules` states the rules in full: `free` and `slots` count only countable nodes (schedulable, every fact known), `configured` and `allocated` also count unschedulable ones, a node with a missing fact or a malformed record is in `unknown_nodes` and in no sum (beside a nonzero `unknown_nodes` the numbers are lower bounds), and a value with nothing known behind it is null, never 0. A node in several requested partitions is in each of their groups and once in `union`, and `by_sku` and `by_class` split the same nodes in two ways: never add groups or breakdowns together. It is a snapshot heuristic at `queried_at`: it does not model fairshare, QOS or partition limits, reservations, preemption or pending work, reserves nothing and predicts no start. It ranks nothing: no recommended partition, shape or GPU model. Summaries of live node records and the `CLASS:` prefix are not observed live.
- `shk status --job-id ID --details` (repeatable ID, mutually exclusive selector) reads current UID legacy or shk jobs. `details.queue` and `details.accounting` retain raw records with cluster, DBIndex, physical/array IDs, times, UID, Comment, TRES, nodes, restarts and exits. `details.jobs` retains queued physical `scontrol` identities with original `fields` and `raw` for request verification. `names` has one entry per selected base job, in job id order; scontrol times are UTC like the rest. A failed `squeue` or `sacct` read is exit 1 `malformed_read`. A cost is final only when `details.missing_job_ids` is empty and the entry's `cost.final` is true. The token (Comment) is visible only while the job is in the controller: Sherlock keeps no Comment in accounting. Incomplete evidence or missing IDs is explicit; do not treat it as permission to resubmit.
- `shk release --job-id ID --expect-name NAME --expect-token TOKEN` releases only a verified exact current-UID job held by `submit --hold --submission-token TOKEN`; both expectations are required. On a borrowed partition a release needs the same occupancy check, budget and window as a submission (see Occupancy below).
- `shk requeue --self --expect-name NAME [--expect-token TOKEN]` runs only with the local executor inside the allocation: it needs real Slurm PID membership in the current physical allocation, the current UID and name, RUNNING, a listed, non-borrowed partition and Requeue=1, which `submit` sets by default only for a `requeue=yes` partition, alone or in a set; on such a partition a job without Requeue is refused `policy`, and a job on a borrowed or unlisted partition is refused `partition`. The token is compared with Slurm Comment only when given. An array element is requeued as `ARRAYJOBID_TASKID`, never the whole array. Lost mutation replies remain unknown (exit 5); never retry blind. Checkpoint durability and maximum retries belong to the project controller.
- `shk update --job-id N --expect-name NAME [--expect-token TOKEN] (--time DUR | --partition P[,P...] | --throttle M | [--constraint X] [--prefer X])` changes one field group of a verified exact current-UID job per call: `--time`, `--partition`, `--throttle`, or the features group, `--constraint` and/or `--prefer` in one call (Slurm tries Prefer instead of Features, not in addition to it, so both must carry every hard requirement). No group or several groups is exit 1 `spec_invalid`: run one update per group. `--job-id` is a plain job id or an array's ArrayJobId; an element `N_TASK` is exit 1, since an update addresses the whole job or the whole array. `--expect-name` is required and `--expect-token`, when given, is compared with Comment, both on every record. `--time`, `--partition` and the features group change only a job whose every record is PENDING. `--time` takes the forms of `submit --time`, rounded up to whole minutes, and only decreases the limit, never below TimeMin: an increase is refused, a shk choice, although Slurm accepts one while the job is pending. `--partition` takes a listed, non-borrowed partition or set of batch partitions as in Submit whose requeue default, on when a member allows requeue, equals the job's Requeue flag, whose members all allow GPUs when the job requests them and whose MaxTime is at least the job's TimeLimit. So a requeueable job moves only to `owners` or a set with `owners`, any other job only to a target without it; dropping `owners` from a pending set is cancel and resubmit for a job submitted with the default requeue; a job submitted `--no-requeue` to a set with `owners` cannot be moved to a set with `owners`, its own included (refused `requeue`, not `unchanged`); the job's current partitions are not checked, so a job pending on a borrowed or unlisted partition can move to a listed non-borrowed target with its requeue value. `--constraint` and `--prefer` take a nonempty value of at most 1024 bytes made of letters, digits and `_.:+*&|()[]-` (no whitespace, `,` or `=`), and cannot clear a value. `--throttle M` (1 to 1000; 0, no limit, is not accepted) needs an array's ArrayJobId and works in any state. A borrowed target is refused (see Occupancy below). A malformed value is exit 1 `spec_invalid` and any other failed check exit 3; neither dispatches anything. When every record already shows the requested value the reply is `action: unchanged` (exit 0) and nothing is dispatched. Otherwise shk dispatches one `scontrol update` and takes the outcome only from one re-read of every record, whatever `scontrol` exited: `updated` (exit 0) when every record shows the requested value, else exit 5 `unknown` with a `next` of `shk status --job-id N --details`; never retry blind. The reply carries `field`, `requested`, the `before` and `after` records and `slurm_messages`, Slurm's text or null. The job keeps its job id, dependencies, begin time and hold. Slurm checks feature names against the nodes of the whole cluster, not of the job's partitions: a feature that no node of those partitions has is accepted and the job never starts, so first check the features that `shk resources --partition P` reports for each of the job's partitions. A partition move can lower the job's age priority until the next scheduler pass, or restart it where accrue limits apply. Update writes nothing locally: the frozen spec keeps the submitted request, so `status --task` still derives `ran_on` from the spec's partition list, while Slurm's records and the reply carry the current request. Anything else, such as CPUs, memory, GPUs, tasks, array size, script, signal, dependencies, the requeue flag, begin time, nice, the token, clearing a constraint or prefer, a throttle of 0, or a running job's walltime, partition or features, needs `shk cancel` and a new `shk submit --resubmit "reason"`. On Sherlock (Slurm 25.11.9) time, features and throttle updates of held pending jobs behaved as described, and two updates that Slurm rejected (a partition set that violated an accounting/QOS policy, an unknown feature) kept the record and read as exit 5; a partition move that Slurm accepts and an update of an array with a started task are source-confirmed, not observed live.
- `shk --executor local allocation --pid PID --job-id ID [--step-id N]` inside a job proves that a worker PID of the current UID belongs to that job (and numeric step) on this host through `scontrol pidinfo` and `listpids`, and reports the actual allocated CPUs, GPUs, nodes and raw records; `$SLURM_JOB_ID` and `ARRAYJOBID_TASKID` both select the element's own record. Missing counts stay null and ambiguous or contradictory evidence fails (exit 1). Use it instead of parsing `scontrol` or trusting environment variables. Its last key, `gpu_sku_candidates`, carries the reply's `queried_at`, a fixed `meaning` text and one entry per node record (the local node): `candidates`, the sorted `GPU_SKU:` values among that node's `ActiveFeatures` (`[]` without one); `ambiguous`, true for several candidates, for more than one GPU type in the node's `Gres` and `CfgTRES`, or for a MIG marker (false is no proof of one whole-device model); and `source`, those three fields as printed. These are node labels, candidates for the GPU model: never the device allocated to the job, and no substitute for the job's own device UUID record. GPU types and MIG types in the `Gres` and `CfgTRES` of a live GPU node are not observed live.
- A deterministic controller must keep all actions bounded and authorized, batch status reads at least 60 s apart and stay within its allocation. It must not invoke an LLM or schedule a later agent session.

## Data

```sh
shk push data/inputs /scratch/users/USER/project/inputs
mkdir -p results
shk pull /scratch/users/USER/project/runs/NAME/out results/NAME --validate bundle
```

`shk pull` is payload-only. The `pulled` and `already_present` replies state the contract as their last key, `payload_contract` (`name` `payload-only`, `version` 1, `verified_against` `SHA256SUMS`, `manifest_in_payload` false, `empty_directories_preserved` false, `validator_must_not_write_stage` true):

1. The stage, and so LOCAL, holds exactly the regular files that `REMOTE/SHA256SUMS` lists, and the directories they imply. `SHA256SUMS` itself is neither staged nor promoted; the receipt keeps the sha256 of the `SHA256SUMS` text that pull read (`manifest_sha256`).
2. A manifest lists files only, so an empty remote directory is not created locally. A validator must not require one, and must not create one.
3. The validator gets the stage as its last argument and treats it as read-only: nothing re-verifies the stage after the validator, and whatever it writes is promoted with the data. `validator_must_not_write_stage` states this obligation; the kit does not enforce it.
4. `payload_contract` describes what a pull promotes. On `already_present` LOCAL is not verified again: the pull reads `SHA256SUMS` once more, compares its digest with the receipt, reads no file of LOCAL and runs no validator, so that reply rests on the receipt of the earlier pull.

- `shk push LOCAL REMOTE` copies into REMOTE (absolute, under `remote_root` unless `--anywhere`) and never deletes. Pushed files keep their local modification times, so inputs that are old locally can be purge-eligible on scratch soon after the push: push them shortly before the jobs that read them.
- REMOTE's parent must already exist. For a new remote root, first push a staging directory containing `inputs/` to the root itself, whose parent exists (for example `shk push staging/ /scratch/users/USER/project`). Check that push exits 0 before submitting a job that reads those inputs: a failed or timed-out push can leave a truncated file under its final name, also where a complete older copy was, so rerun it to exit 0 before any job reads REMOTE.
- `shk pull REMOTE LOCAL` needs `REMOTE/SHA256SUMS` and an existing parent directory of LOCAL, copies exactly those files into a private stage beside LOCAL (`.NAME.shk-stage` for LOCAL `.../NAME`, with `.NAME.shk-lock`), verifies every hash, runs the validator named by `--validate`, then renames the stage onto LOCAL and writes `.NAME.shk-receipt.json`. An existing LOCAL is kept unless `--replace` (the old copy stays as `.NAME.shk-old-<UTC>`); a rerun resumes the stage. `already_present` means the receipt beside LOCAL names this manifest: LOCAL is not verified again. An error while REMOTE is enumerated (an unreadable subdirectory) is exit 1 `remote_failed`, and nothing is promoted.
- The validator is the project's argv from `[tool.sherlock-kit.validators]`; it runs from the project root with the stage directory as its last argument, exit 0 passes, and it must treat the stage as read-only (what it writes is promoted).
- The job writes the manifest as its last step: `shk manifest DIR` when shk is available there, else `(cd DIR && find . -name '.shk*' -prune -o -type f ! -name SHA256SUMS -printf '%P\0' | sort -z | xargs -0r sha256sum --) > DIR/SHA256SUMS`. DIR is the job's output directory (for example `out/` under the run directory), never the run directory itself, which holds `.shk/` and the Slurm logs still being written.
- Never touch or rewrite scratch files to keep them from the 90-day purge; copy what must last to `$GROUP_HOME`, Oak or the workstation.

## Occupancy and borrowed partitions

- `shk occupancy --partition btrippe` shows who uses a partition now. Run it before every submission to a borrowed partition (`borrowed=yes` in the rules' partition profiles), read the courtesy text, then submit with `--courtesy-ack`. The submit reply repeats the occupancy and courtesy text and adds `request = {tasks, throttle, minutes}` (tasks is 1 for a single job, else the array count; throttle is null without `%M`) and `warnings`. Two advisories exist and neither refuses: the budget warning, when others are running there and you already have 2 jobs there or ask for more than 2 h; and a total-work advisory, when others are running there and tasks is greater than 2, stating the number of array tasks, the throttle (or that there is none) and the minutes. It reports facts and does not say whether the request is within or over any budget: read them against the courtesy text, which neither advisory replaces.
- Releasing a job held on a borrowed partition counts as submitting it: `shk release` checks neither occupancy nor the clock, so run `shk occupancy` first and release only within the budget and window that a submission would need.
- `shk update` refuses borrowed targets: `--partition` with a borrowed partition is exit 3 (`borrowed_not_allowed` alone, `partitions_incompatible` in a set), and a `--throttle` above the current throttle of an array on a borrowed partition is refused (exit 3). Lowering the throttle there is allowed; an array without a throttle has no limit, so any value lowers it. Instead, cancel, run `shk occupancy`, then submit again with `--resubmit` and `--courtesy-ack`.
- `btrippe`: about 2 jobs x 2 h while others are active; more (for example 4 jobs x 6 h) only when the partition is idle, typically 00:00-07:00. It has no blanket daytime prohibition. `possu`: submit or release only between 00:00 and 07:00 Pacific, a few short jobs. Unlisted partitions are refused; scheduler visibility is never authorization.
- `bioe` and `stat` are not borrowed: no `--courtesy-ack`, and shk counts, warns of and refuses nothing for their terms. Before a submission, a release or a throttle raise that names either, read both in one call, `shk occupancy --partition bioe --partition stat`: stat's courtesy text in the reply refers to bioe's. Your own `running_gpus` per partition (`partitions.P.users`, under the reply's `user`) is what the department loses; `pending_jobs` counts records, so a pending array is one record and a pending set job appears in every partition it lists. Size the request by the department terms in GPU and partition preferences above.

## Cancel

`shk cancel --task train-a` (or `--name NAME`) cancels only the live jobs of that one name and reports their ids and `next_check_after`. A nonzero `scancel` exit is outcome unknown (exit 5, `scancel exit RC` and Slurm's text in `detail`): read status as `next` says before cancelling again. Routine cancellation of exact verified own jobs in an authorized task may proceed; tell the user why (`shk cancel` records no reason). Ask for unclear ownership/scope, unrelated work, broad cancellation, or material irreversible loss of important progress/results. Keep current UID/name filters and unknown-outcome protection; never cancel all user jobs.

## On Sherlock

On a login node or inside an allocation `shk` uses the local executor (no ssh); `SHK_EXECUTOR=local` or `--executor local` forces it. `shk push` and `shk pull` are refused there (exit 3): the data is already on the cluster, and large internal copies run in a Slurm job. Follow `shk rules cluster`.

## Never

- Authenticate for the user, retry a login in a loop, or store passwords or MFA secrets.
- Run raw `sbatch`, `scancel` or `squeue` loops over ssh when `shk` covers the task, or `scancel -u $USER`.
- Poll with `watch` or a `shk status` loop, detach `shk wait` so that it outlives the session, or use a wait to re-prompt an agent.
